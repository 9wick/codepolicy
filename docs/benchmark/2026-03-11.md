## モデル特性分析

### gpt-4.1（GitHub Copilot）— 甘い採点者

- 27 関数中 24 個が **100 点満点**
- ほぼ全て問題なしと判定する傾向
- `getUserProfile` で引数 `id` を `void id;` で無視している明確なバグを **見逃し**（100 点）
- `buildWelcomeMessage` のみ厳しく 45 点

### gpt-5.3-codex — バランス型

- gpt-4.1 に近いがスコアに若干のバリエーション（96-98 点帯が多い）
- `isStringRecord` を 62 点で検出（gpt-4.1 の 60 と近い）
- 途中終了のため全体評価は不完全

### gpt-5-nano — 推論型だが重い

- reasoning tokens を使用（各リクエストで 512-1216 tokens）
- スコアは 85-100 が多く適度な厳しさ
- メモリ消費が大きく SIGKILL で途中終了

### claude-haiku-4-5 — 厳格な採点者

- 7 つの violation を検出（最多）
- **真に正当な指摘が多い**:
  - `isStringRecord(25)`: 値の型検証が欠落（全モデル一致）
  - `getUserProfile(25)`: `void id;` で引数を無視（gpt-4.1 は見逃した）
  - `toArrayIfPresent(65)`: truthiness 判定と null 判定の差異
  - `buildIncludedContextSections(55)`: 戻り値の型が名前と不一致
- **false positive 的な厳しさ**も存在:
  - `main(45)`: 他モデルは 88-100 で問題なし
  - テスト関数に対する過剰な厳格さ

### minimax-m2.5-free — 不安定

- StructuredOutput 生成に頻繁に失敗
- 動作時のスコアは妥当だが実用に耐えない

## 真のバグ検出精度

`isStringRecord` は全モデルが正当に FAIL と判定した唯一の関数。

| 指標 | gpt-4.1 | gpt-5.3-codex | gpt-5-nano | haiku |
|------|---------|---------------|------------|-------|
| 真のバグ検出（isStringRecord, getUserProfile） | 1/2 | 1/1* | 1/1* | **2/2** |
| 適度な指摘（toArrayIfPresent 等） | 0 | 1 | 0 | **3** |
| false positive 的な厳しさ | 0 | 0 | 0 | 2-3 |

\*途中終了のため getUserProfile まで未到達

## 結論

| 観点 | 最優秀モデル |
|------|-----------|
| 安定性・信頼性 | gpt-4.1, haiku（完走） |
| バグ検出精度 | **haiku**（真のバグを最も多く検出） |
| false positive 率の低さ | **gpt-4.1**（ただし見逃しあり） |
| コスト効率 | gpt-4.1（cache hit 率が高い） |
| 実用不可 | cerebras（モデル不存在）, minimax（不安定） |

CI 用途では **gpt-4.1 で一次スクリーニング → haiku で精密チェック** の 2 段階が有効と考えられる。
